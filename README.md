# PII Redaction Tool

A reproducible Python pipeline that detects personally identifiable information in DOCX/PDF input and writes a separate redacted DOCX. It uses validated regular expressions, context-aware rules, and an optional spaCy NER adapter rather than an external paid API.

## Scope of the two evaluation sets

This repository holds two clearly separated result sets and they are never mixed.

| | Synthetic fixture | Real source document |
| --- | --- | --- |
| Input | `input/synthetic_rhp_fixture.docx` | the supplied RHP, read-only, never modified |
| Redacted output | `output/redacted_rhp.docx` | `output/real_rhp_redacted.docx` |
| Annotations | `evaluation/ground_truth.json` | `evaluation/real_rhp_ground_truth.json` |
| Predictions | `evaluation/predictions.json` | `evaluation/real_rhp_predictions.json` |
| Report | `evaluation/evaluation_report.md` | `evaluation/real_rhp_evaluation_report.md` |
| Verification | `evaluation/verification.json` | `evaluation/real_rhp_verification.json` |

The fixture is generated by `tools/create_demo_fixture.py` and every value in it
is fabricated; it is a regression harness, not evidence. The real-document set
is scored against annotations produced independently from the source text under
`docs/annotation_policy.md`.

The real RHP is **not committed** to this repository, and neither are the derived artefacts that reproduce source values: `evaluation/real_rhp_ground_truth.json` and `evaluation/real_rhp_predictions.json` are listed in `.gitignore` and are regenerated locally with the commands below. `output/real_rhp_redacted.docx` *is* tracked, because it contains only reserved/test replacement values and is safe to share. `evaluation/real_rhp_evaluation_report.md` is tracked and never prints an entity value.

## Approach

### Detection

The real RHP exposes two hard cases that the per-paragraph rules alone do not
solve, so detection runs in three passes.

- **Structured values:** case-insensitive email matching; `ipaddress` validation for IPv4/IPv6; US SSN format plus allocation checks; Luhn validation and length checks for card candidates; context/length checks for phones. A phone or card match can be vetoed by an identifier label sitting **before** the value, so registration, order, ticket, and reference numbers stay in the clear.
- **DOB:** numeric and textual dates are accepted only when `DOB`, `Date of Birth`, `Birth Date`, or `Born` is immediately associated with the value. Filing, transaction, and financial dates are not classified as DOBs.
- **Addresses:** complete address-like spans are selected using house/building numbers, street/locality keywords, commas, and postal-code structure. A semicolon-delimited contact line is split into fields so a following phone number is not swallowed by the address. A short, self-contained table cell that carries an address keyword or a PIN counts as its own context, so a layout that spreads one address over several cells is still redacted (`<City> - <PIN>`, `<Building> Centre`). A leading building or unit designator is kept inside the span (`<Building> Apartment, Flat - 1, ...`, `Unit no. 1601, ...`) because trimming it would leave the building name in the clear. A location preposition introduces the value after it, so prose that ends `... sent to <name> at <house>, <street>, <city> <PIN>` redacts the address and not the sentence.
- **People:** title/role/label rules plus a small, general first-name fallback heuristic. This avoids treating every capitalized phrase as a name. `spacy` is loaded only if a compatible model is available; it is not a hard dependency.
- **Organizations:** legal suffixes (`Pvt. Ltd.`, `Limited`, `Inc.`, etc.) and organization-label context are used. Under this assignment's explicit policy, detected organization names are treated as sensitive; this is a deliberate precision/recall tradeoff discussed below.
- **Document-level propagation:** a person or organization confirmed elsewhere in the document is re-detected in the formatting variants and positions the local rules miss, including all-caps runs and multi-token names.
- **Cross-unit values:** a name laid out over consecutive cells (`<ACME> | <Place> | Private Limited`) or across paragraph boundaries is found by a bounded window pass, and **every fragment is redacted** so the value cannot be reassembled from what remains. A single-token half is accepted on a case-insensitive boundary-token check, which matters because the same name appears in both title case and all capitals. A fragment is not a value, so the residual check tests for the whole name rather than the piece that was printed in one cell.
- **Overlap resolution:** a complete address wins over a nested phone/email-like substring; structured card/SSN/email/IP matches win over generic phone matches. This prevents double counting.

### Replacement and document handling

`ReplacementRegistry` maps normalized `original value + PII type` to one deterministic synthetic value, so repeated values remain consistent. Faker supplies seeded names; the fallback implementation works without Faker. Replacements use reserved/test values where appropriate (`@example.com`, `203.0.113.0/24`, the public `4242...` payment-test number, and an invalid-allocation `900-xx-xxxx` SSN).

For DOCX, the processor edits `w:t` nodes in document paragraphs, table cells, headers, footers, notes/comments when exposed, hyperlinks, and text-box paragraphs. It retains existing styles and run properties as far as practical and updates `mailto:` hyperlink targets. Runs split mid-value are handled, and hyperlink targets are rewritten whether the target lives in a relationship part or in a `w:instrText`/`w:fldSimple` field code; the real RHP uses 105 field-code hyperlinks and 0 relationship hyperlinks, and all 105 are rewritten. The output is reopened before it is reported as successful. PDF input is extracted with `pdfplumber` into page-labelled paragraphs; PDF visual layout is not claimed to be perfectly round-tripped.

## Supported PII types

`PERSON`, `EMAIL`, `PHONE`, `ORG`, `ADDRESS`, `SSN`, `CREDIT_CARD`, `DOB`, and `IP` (IPv4 and validated IPv6).

Ambiguous entities are handled conservatively: a lone city/state is not an address, an arbitrary long number is not a phone/card, and an ordinary date is not a DOB. Organization names are intentionally included because the assignment explicitly requires them, even though an organization is not always personal information in ordinary legal documents.

### What is deliberately *not* redacted

This is a policy choice, stated explicitly so it can be argued with. The tool
detects **natural persons, legal entities, physical addresses, and contact
details**. It does **not** treat the following as PII, so they are left in the
clear:

| Category | Examples | Why |
| --- | --- | --- |
| Company registration identifiers | `CIN`, `GSTIN`, `PAN`, `DIN`, registration and licence numbers | Public registry data about an entity, not a person's identity |
| Transaction references | order, ticket, invoice, transaction, cheque and receipt numbers | Pointers to a business event, not a person |
| Dates | filing, board-meeting, incorporation and financial-year dates, and ranges such as a fiscal year | Ordinary business dates; only an explicitly labelled `DOB` is treated as sensitive |
| Figures | share counts, revenue and page numbers | Not personal data |
| Place names without an address structure | a bare city/state pair, a country, a market or region | A market is not an address; see `docs/annotation_policy.md` for the exact split |

A number in one of these contexts is suppressed only when the identifying label
sits **before** it: `Ticket No. 9876543210, please contact us` is a ticket
number, because `contact` describes the sentence and not the number, while
`Contact number 9876543210` is a phone number. A card word overrides the generic
word `number`, so `Card number 4111 1111 1111 1111` is still redacted.

If a deployment needs any of these treated as sensitive, they are the cheapest
types to add: see [Extensibility](#extensibility).

Python 3.10+ is recommended (the project was tested with Python 3.12).

```powershell

python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### macOS/Linux

```bash
cd /path/to/pii-redaction-tool
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Optional NER support:

```bash
python -m pip install spacy
python -m spacy download en_core_web_sm
```

Without that model, the built-in contextual fallback is used automatically. For a deterministic run in this repository, the commands below use `--no-spacy`.

## Usage

Run the included synthetic fixture end-to-end:

```bash
python run.py --input input/synthetic_rhp_fixture.docx --output output/redacted_rhp.docx --predictions evaluation/predictions.json --ground-truth evaluation/ground_truth.json --report evaluation/evaluation_report.md --no-spacy
```

Run against a real document (the input is never overwritten):

```bash
python run.py --input path/to/original_rhp.docx --output output/real_rhp_redacted.docx --predictions evaluation/real_rhp_predictions.json --no-spacy
python -m src.evaluation --ground-truth evaluation/real_rhp_ground_truth.json --predictions evaluation/real_rhp_predictions.json --output evaluation/real_rhp_evaluation_report.md
python tools/verify_output.py --input path/to/original_rhp.docx --output output/real_rhp_redacted.docx --predictions evaluation/real_rhp_predictions.json --report evaluation/real_rhp_verification.json
```

PDF input is also accepted and produces a DOCX output:

```bash
python run.py --input path/to/original_rhp.pdf --output output/redacted_rhp.docx --no-spacy
```

Regenerate the explicitly synthetic demonstration fixture if needed:

```bash
python tools/create_demo_fixture.py
```

Run the automated tests:

```bash
python -m pytest -q
```

Validate annotation spans and inspect the generated package:

```bash
python tools/validate_ground_truth.py --source input/synthetic_rhp_fixture.docx --ground-truth evaluation/ground_truth.json
python tools/verify_output.py --input input/synthetic_rhp_fixture.docx --output output/redacted_rhp.docx --predictions evaluation/predictions.json --report evaluation/verification.json
```

Rebuild a ground-truth set for a new source document:

```bash
python tools/make_ground_truth_chunks.py --source path/to/document.docx --chunks review_units
# annotate the emitted units_NN.txt files as gt_NN.jsonl, then:
python tools/merge_ground_truth.py --chunks review_units --output evaluation/real_rhp_ground_truth.json --report merge_report.json
python tools/validate_ground_truth.py --source path/to/document.docx --ground-truth evaluation/real_rhp_ground_truth.json
python tools/audit_ground_truth.py --source path/to/document.docx --ground-truth evaluation/real_rhp_ground_truth.json --predictions evaluation/real_rhp_predictions.json --output audit.json
```

## Evaluation

`evaluation/ground_truth.json` contains manually checked annotations for the synthetic fixture, with repeated occurrences separated by DOCX unit ID. A prediction is a true positive only when its normalized text and category match an annotation; an exact unit/location and compatible context are used to disambiguate repeats. A wrong category is a false positive for the predicted category and a false negative for the true category. Complete addresses are scored as one entity, so a PIN inside an address is not counted separately.

Because arbitrary text spans do not have a finite, meaningful true-negative set, ordinary binary `accuracy=(TP+TN)/(TP+TN+FP+FN)` would be misleading. The report uses the explicitly named open-world **entity-decision accuracy**:

```text
accuracy = TP / (ground_truth + FP)
```

The report also calculates standard precision, recall, and F1. On the included synthetic fixture, the verified result is:

| Metric | Result |
| --- | ---: |
| Ground-truth entities | 26 |
| Predictions | 26 |
| TP / FP / FN | 26 / 0 / 0 |
| Entity-decision accuracy | 100.0% |
| Precision | 100.0% |
| Recall | 100.0% |
| F1 | 100.0% |

These numbers are a regression result for a deliberately controlled fixture, not evidence of performance on a real document.

### Real source document

The real RHP was annotated independently under `docs/annotation_policy.md`, in 21 review chunks, and the resulting set of 631 annotations was validated with `tools/validate_ground_truth.py`: every span was re-derived from the source text and 0 errors were reported. A second pass then reviewed the gaps in both directions against the detector output, and every span change is recorded in an audit trail (`qa_corrections.log`) next to the annotation chunks, so a reviewer can tell which decisions were made from the text and which were made on review.

Command used:

```bash
python run.py --input "<source>.docx" --output output/real_rhp_redacted.docx --predictions evaluation/real_rhp_predictions.json --no-spacy
```

| `ORG` | 253 | 226 | 226 | 0 | 27 | 100% | 89.3% |
| `ADDRESS` | 75 | 67 | 67 | 0 | 8 | 100% | 89.3% |
| `EMAIL` | 52 | 52 | 52 | 0 | 0 | 100% | 100% |
| `PHONE` | 36 | 36 | 36 | 0 | 0 | 100% | 100% |
| `SSN` | 0 | 0 | - | - | - | N/A | N/A |

`SSN`, `CREDIT_CARD`, `DOB`, and `IP` are reported as `N/A - no instances present in source`. A mechanical sweep of the whole document found no value of any of those four shapes outside an address, so a perfect score is not claimed for them.

Every prediction matched an annotation: **precision is 100% and there are no false positives at all.** Read that number for what it is: precision is measured against annotations produced under the policy in `docs/annotation_policy.md`, so it shows the detector agrees with the annotator and contains nothing the policy did not call PII. It is not evidence that the policy is complete, and it is blind to a PII class that was never annotated. All 47 misses are recall gaps, and they fall into three clusters rather than being scattered noise:

| Missed class | Count | Why it is missed |
| --- | ---: | --- |
| Bare trading / brand name used as a party | ~18 | `ORG` is keyed on a legal suffix or a label, so a column that writes a brand alone is not matched. The full legal name appears elsewhere in the document but does not help, because propagation matches whole values, not aliases. The affected values are listed in the ground truth and are not reproduced here. |
| One-off director names | 12 | A person name with no title, no role prefix, and no second occurrence in the document. Propagation cannot help a name that appears exactly once. |
| Short address forms | 8 | Bare house-number lists and locality-only cells with no street, keyword, or PIN to give the structural rules anything to work with. |

The first cluster is the most systematic and the most worth fixing: an alias table built from the document's own full names (`<Brand>` -> `<Brand> Private Limited`) would recover most of it, but that is a design change rather than a tuning fix, and it is left as the next step rather than folded into this result.

`evaluation/real_rhp_evaluation_report.md` breaks the 47 misses down individually, describing each by category, span shape, token count, and unit id only.

To reproduce or audit these numbers, the cross-check tool reports gaps in both directions without printing a single value:

```bash
python tools/audit_ground_truth.py --source "<source>.docx" --ground-truth evaluation/real_rhp_ground_truth.json --predictions evaluation/real_rhp_predictions.json --output audit.json
```

The report itself never prints an entity value: unmatched entities are described by category, span shape, token count, and unit id only. The annotation and prediction JSON files do contain original values by design, are untracked, and must be handled as sensitive evaluation artifacts.

## Tradeoffs and observed errors

- The synthetic fixture scores 100% on every metric; the real document is where the interesting cases live, and the metrics above are from the real document. A perfect fixture result is a regression check on the rules, not a performance claim.
- **The dominant false-negative class is the bare trading/brand name.** A party column that writes a brand on its own in one place and the full legal name elsewhere is missed, because the detector keys on a legal suffix or a label rather than on a learned alias. This is the largest recall gap and the most systematic one; the example values are in the ground truth and are deliberately not reproduced here.
- **Person names outside the local heuristics are missed**, almost entirely independent and executive directors in the board table whose names carry no title, no role prefix, and no occurrence elsewhere in the document. Document-level propagation cannot help here because the name appears once.
- **Layout-split organisation names are detected and every fragment is redacted**, but the fragment itself is not a name: `Limited` alone is annotated and redacted because leaving it next to a redacted neighbour is what makes a value reassemblable. This is intentional and documented in the annotation policy, and it is why the ground truth annotates fragments too.
- Treating every detected organization as sensitive satisfies the assignment's required organization category but can redact non-personal organizations. This is a conscious scope choice.
- The fallback name detector can miss names outside its small first-name list. Role/label rules and optional domain-appropriate NER improve recall but may increase false positives.
- A card match needs Luhn validation *and* no contradicting identifier label, so a Luhn-valid sixteen-digit registration or reference number is left alone. The label test is a keyword heuristic: a card value sitting in a cell with no label at all, or one whose neighbouring words happen to include an identifier word, can still be classified wrongly. In a high-stakes deployment the candidate should be reviewed rather than auto-redacted.
- SSN detection rejects arbitrary contiguous nine-digit numbers without an SSN label. The real RHP contains no SSN, credit-card, DOB, or IP values; those categories are reported as `N/A - no instances present in source`, not assigned a perfect score. A mechanical sweep of the real document also found 16 phone-shaped strings that are **not** phone numbers (financial-year ranges, a regulator circular number, and 8-digit director identification numbers); the annotation policy records that DIN/PAN/CIN are identifiers, not contact details.
- PDF extraction can lose layout and reading order. The generated DOCX preserves extracted text/page boundaries, not the original PDF's exact visual design.
- Synthetic replacement values are deliberately non-production values. Do not use them as real identities, credentials, or contact details.

## Extensibility

1. Add a `PIIType` member in `src/models.py`.
2. Implement a detector returning an `Entity` with precise offsets in `src/detectors.py`.
3. Add its call to `PIIDetector.detect` and define overlap priority if it can nest inside another span.
4. Add a deterministic synthetic branch in `ReplacementRegistry.replacement_for`.
5. Add positive, negative, overlap, and document round-trip tests.
6. Add the category to `SUPPORTED_TYPES`; the evaluation and report tables then include it automatically.

Steps 1-3 and 6 are the only places a new type has to be named. The report
tables, the per-type replacement bookkeeping, and the used-value pools all
iterate `PIIType`/`SUPPORTED_TYPES` rather than hard-coding a list, so a new
category appears in the metric tables automatically. The three genuinely manual
parts are the detector, the `replacement_for` branch in step 4, and the
`docs/annotation_policy.md` rule that tells an annotator what to label.

`src/detectors.py` is the one file that has grown past comfortable size
(~1,900 lines). It is already divided into banner-marked sections in a fixed
order — regex vocabulary, shared helpers, one group of functions per PII type,
then overlap resolution and the NER adapter — and the sections are largely
independent, so splitting it into `detectors/<type>.py` behind the existing
`detect_*` function names is a mechanical move. It is left as-is because the
split is a refactor with no behaviour change, and doing it alongside a
behaviour change would make the two indistinguishable in the diff.

## Verification

A redacted document is only useful if the original values are provably gone, so the run ends with checks rather than with a success message.

`tools/verify_output.py` opens the produced DOCX and confirms all of the following, exiting non-zero on any failure:

1. **No original value survives in the text.** Every detected value is searched for using a whole-value pattern, not a substring test: `(?<![A-Za-z0-9_])value(?![A-Za-z0-9_])` with `\s+` between tokens. A substring test would report `Broad` surviving inside `abroad` and would miss a value re-flowed across runs.
2. **No original value survives anywhere in the package XML**, not just in the body text, so a value cached in a `w:instrText` field, a relationship, or a header/footer part is caught.
3. **No stale hyperlink.** Both relationship targets and `HYPERLINK "mailto:..."` field codes are scanned for a surviving address.
4. **Every unit that carried an original value was actually rewritten**, reported as a per-unit check rather than a global count.
5. **The output reopens** with `python-docx`, and SHA-256 digests of the input and output are recorded.

The value used for the check is the entity's `identity` when it has one, not the fragment `text`, because a cross-unit fragment is not a value: the whole name must be gone, not just the piece that was printed in one cell.

The verification report contains counts, digests, and unit ids. It never prints an entity value.

## Verification performed

On the real RHP: the pipeline was run with `--no-spacy`, the output reopened, all 105 hyperlink field codes checked for stale targets, the full package XML searched for every original value, and `python -m compileall` and `python -m pytest -q` run clean. The source document was opened read-only throughout; its digest is `8b5c93f7…6f929`, recorded in `evaluation/real_rhp_verification.json`.

The **input** digest is the stable one and is the way to confirm you are looking at
the same source. The **output** digest is not reproducible: two runs on the same
input produce byte-identical parts inside the DOCX but different file digests,
because a zip records a build timestamp per entry. What is reproducible is the
detection result — the predictions list is byte-identical and identically ordered
across runs, which is what the metrics depend on. Do not treat a changed
`output_sha256` as a regression; compare the prediction counts and the metrics.
